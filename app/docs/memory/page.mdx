# Memory

An agent's usefulness depends on what it can remember. Eve gives every agent memory at three layers, and Studio's **Memory** tab shows all three for the active agent and lets you add the ones it doesn't have yet.

## Three layers

### 1. Session memory (built in)

Every Eve conversation is a **durable session**: long-lived, survives process restarts and redeploys, and can span many messages over days or weeks. Within a session the agent keeps its full history in order. As the context grows, Eve **compacts** it: it writes a checkpoint summarizing earlier history so the conversation can continue without overflowing the model's context window. This is automatic; you can also trigger it from Chat with **Compact context**.

Alongside history, Eve gives a session:

- **Durable state**: `defineState` holds working data for one session (a plan, a counter) and dies with the session.
- **A todo list**: the built-in `todo` tool keeps a per-session task list that survives compaction.
- **A sandbox workspace**: files the agent writes under `/workspace` in its sandbox persist for the session.

The boundary matters: session memory remembers *within a conversation*. A new session starts fresh, and a subagent gets its own separate session. The Memory tab shows this layer for information; there's nothing to configure.

### 2. Memory slots

A **memory slot** gives the agent context that outlives a session. Eve owns the slot (its name, whose memory it is, and when recall and capture run); a **provider** owns the storage and retrieval. Each slot is one file under `agent/memory/`:

```ts title="agent/memory/profile.ts"
import { defineMemory } from "eve/memory";
import { byPrincipal } from "eve/memory/scope";
import { fileMemory } from "eve/memory/file";

export default defineMemory({
  description: "Remember stable facts and preferences about the caller.",
  provider: fileMemory(),
  scope: byPrincipal,
});
```

Before each turn Eve asks the provider to recall relevant context, after each turn it lets the provider capture what happened, and any tools the provider offers reach the model as `<slot>__<tool>` (here `profile__save_memory` and `profile__remove_memory`). `scope` decides who shares the memory; `byPrincipal` scopes it to the authenticated caller and uses a shared `local-dev` scope while you iterate locally.

Providers:

| Provider | Ships as | Recall | Capture |
| --- | --- | --- | --- |
| **File memory** | built into eve (`eve/memory/file`) | one bounded document per scope | model-driven `save_memory` / `remove_memory` |
| **Supermemory** | `@supermemory/eve` via `eve add memory/supermemory` | semantic search | automatic after each turn, plus tools |
| **Your own** | your code | whatever your store returns | whatever rules you implement |

File memory needs no external service in `eve dev` and stores to a private Vercel Blob store when deployed to Vercel (attach a Blob store to the project). Supermemory needs `SUPERMEMORY_API_KEY`.

Slots are independent and a subagent declares its own under its directory. Extensions cannot contribute slots, which is why Arcana (below) is an extension rather than a provider.

### 3. Long-term memory with Kybernesis Arcana

[**Kybernesis Arcana**](https://eve.dev/integrations/arcana) is an official eve integration for workspace-scoped long-term memory: recall, storage, and brain notes, with embeddings and a timeline. It installs as an **extension mount**:

```bash
eve add extension/arcana
```

That installs `@kybernesis/arcana` and writes the mount:

```ts title="agent/extensions/arcana.ts"
import arcana from "@kybernesis/arcana";

export default arcana({
  apiKey: process.env.ARCANA_API_KEY!,
  workspace: process.env.ARCANA_WORKSPACE!,
});
```

The mount contributes, under the `arcana__` prefix:

- an **MCP connection** to Arcana's memory service (`arcana__memory`), exposing tools such as `arcana_recall`, `arcana_search`, `arcana_timeline`, `arcana_remember`, and the `arcana_brain_*` note tools;
- **skills** `recall`, `remember`, and `brain-note`;
- always-on **instructions** that tell the model to search the workspace before claiming ignorance, and never to store passwords, tokens, payment data, private keys, or one-time codes.

Because the instructions ship with the extension, you don't add a memory section to `instructions.md` yourself. Two environment variables configure it: `ARCANA_API_KEY` (a workspace-scoped `kb_…` key; keep it in a sensitive env var) and `ARCANA_WORKSPACE` (the brain this agent reads and writes). A subagent can carry its own mount under `agent/subagents/<id>/extensions/arcana.ts` pointed at a different workspace, giving it a separate brain.

## The Memory tab

Open an agent and select the **Memory** top tab. It reads the agent's compiled manifest and shows:

- **Session memory**: always present, as one expandable row; open it for what Eve keeps per session.
- **Memory slots**: every slot under `agent/memory/`, with its provider (file memory, Supermemory, or custom), scope, and the tools it exposes. **Add file memory** scaffolds `agent/memory/profile.ts` like the example above. **Add Supermemory** runs `eve add memory/supermemory --non-interactive --yes` and tells you which env var to set. Click a slot to open its source in the editor.
- **Arcana**: whether the official extension is mounted, the workspace it points at, and which key variable is present. Studio reads the workspace from the mount file itself, so a literal string, `process.env.ARCANA_WORKSPACE`, and a fallback such as `process.env.ARCANA_WORKSPACE ?? "default"` all resolve; the key is reported by the env var the mount reads (normally `ARCANA_API_KEY`). If Arcana isn't mounted, the **Connect Arcana** flow below wires it. Agents that were wired the old way, with a hand-written MCP connection at `agent/connections/arcana.ts`, show as **legacy connection** with a **Migrate** button that installs the official extension in its place.

## Connecting Arcana in Studio

**Connect Arcana** asks for two things:

- **A workspace**: the Arcana brain this agent reads from and writes to.
- **An API key**: the `kb_…` key that authorizes that workspace.

Then Studio:

1. **Validates the key** read-only against the Arcana API (a `GET …/timeline?limit=1` must succeed).
2. **Installs the extension** with `eve add extension/arcana --non-interactive --yes --skip-setup`.
3. **Sets `ARCANA_API_KEY` and `ARCANA_WORKSPACE`** in `.env.local`, and, if the agent is linked to Vercel, pushes both to the project's environment so the deployed agent has them too.
4. **Restarts** the dev server so the mount is live.

If `eve add` fails at the dependency-install step (see [Troubleshooting](/docs/troubleshooting#eve-add-failed-with-dependency_install)), Studio installs `@kybernesis/arcana` with the agent's package manager and writes `agent/extensions/arcana.ts` itself. Either way the result is the same mount.

Keep the key out of source. It lives as an environment variable, never in code.

## The brain browser

Once Arcana is connected, the Memory tab opens a **brain browser** for the workspace:

- **Stats**: how many memories, entities, and notes the brain holds.
- **Timeline**: the most recent things the agent remembered, across every surface it runs on (Studio chat, Slack, schedules).
- **Search**: query the brain the way the agent's `arcana_search` tool does.

It reads the same workspace the agent writes, so what you see is what the agent will recall.
